## Carried-over rules
- All `.conf` output through the one escaping writer; newlines in values rejected.
- TA names `TA-parsemaxxing-<vendor>-<product>`, parts match `^[a-z0-9_:-]+$`, resolved paths stay inside the TA folder.
- Generated add-ons carry no Parsemaxxing licence: never write `LICENSE`, `NOTICE` or PolyForm text into a TA; its `README.txt` says only "Generated with Parsemaxxing".
- Legacy names: add-ons built before the rename keep `TA-parsewright-<vendor>-<product>`. The name guardrail accepts that prefix only for names already in the ledger; every new add-on uses `TA-parsemaxxing-`. Never rename a deployed app in place (master prompt section 4).
- Test deploys only to sandboxes, always under the test identity; the shared `pmx_` test index only; never create or delete indexes.
- The Validator is code plus fixed SPL, no AI, `earliest=0` for test data.
- Search command allowlist, row and time caps; never `delete`, `collect`, `dbxquery`, `loadjob`, custom commands.
- CIM definitions always come from a CIM add-on (read per environment, see below), normalized and stored by code; never generated by a model.
- Every guardrail change needs an adversarial test.

## CIM definitions, specs and formats (design 7.12, 7.16, 7.17)
- **CIM library (design 7.16):** the admin uploads the `Splunk_SA_CIM` package per version. Read the version from `default/app.conf`, extract only `default/data/models/*.json` and `app.conf` with the safe-tar rules (never run anything from it), normalize every model, store per (version, model) with hashes. Refuse versions outside the compatibility table. Each environment uses only the package with exactly its installed version (read from `apps/local/Splunk_SA_CIM`, or entered by the admin); no match blocks CIM work for that environment with "Upload Splunk_SA_CIM <version>". When the read account can reach the environment, compare its `datamodel/model` definitions with the package by hash and report local changes per model; the admin picks package or environment definitions. Install the same library package on sandboxes (replaces the manual `lab/` drop). Never commit the package; `cim_spec.json` is a test fixture only.
- **Fit score (code), after extraction:** build a value profile per extracted field from Splunk (`fieldsummary` and value counts: coverage, distinct count, top values, value shape such as IP, port, MAC, email, domain, URL, user, numeric, enum); score every model and dataset by required fields whose source value shape fits the CIM type, tags the categories can produce, and enum values that can map to expected values. Names are hints only. Check the agent's field-level plan: each named source field exists with a fitting value shape, each enum mapping covers every value seen (unmapped values reported with counts). Code then bounds the CIM mapper's selection: only that CIM version's models, a minimum fit unless the reason is flagged, never a model whose required tags the categories cannot produce; "no CIM model fits" is allowed. After selection, the mapper receives only the chosen models' definitions.
- **Deployment re-check:** the plan compares the package's CIM mapping with the target environment's definitions and blocks on a missing field, tag or value with the exact difference.
- **Spec bundles:** collect from the sandbox mount, an admin upload or the relay's read-only `specs` verb; parse the spec format with code (no AI) into per-version records; build the per-version key table the gate checks (unknown key blocked, deprecated key warned). Never commit Splunk's spec, example or default files; tests use spec-format files written for the tests.
- **Formats:** code detection signatures per format feed the Profiler as a hint; per-format gate keys (typed, bounded, each with adversarial tests); per-format validator rules (event counting, header lines excluded, CEF/LEEF unescaping and XML entity decoding before value checks). XML parsed in engine code only with `defusedxml`; JSON and CSV parsing capped in size and depth. `INDEXED_EXTRACTIONS` and related keys only if the lab (Q20) decides for them, and then placed on the forwarder or first parsing tier by the plan.

## Add-on package store and comparisons (`ta_store/`, design 7.15)
- Content-addressed and write once: `<sha256>.tgz`; write to a temp file, verify the hash, atomic rename, then read-only. Never overwrite an existing key, never delete one; there is no delete function at all.
- Every read verifies the hash; a mismatch raises an integrity error and the version is shown as "integrity failed". Never fall back to another copy silently.
- Read files straight from the stored `.tgz` in memory with the safe-tar rules and the package file allowlist; never extract to disk; cap file size.
- Compare any two versions: file level (added, removed, changed), setting level per `.conf` (stanzas and keys, parsed by the same conf parser the gate uses), and text per file. Output is structured rows for the UI, never unified-diff text.
- "Compare with installed": a version vs an environment's effective settings read back over REST, with `local/` overrides flagged.
- **Masked regression sets (design 7.19):** at registration, build a fully masked copy of the samples (7.10 rules plus a stricter pass for unclassified long free text), re-run the version's sandbox checks on it and a secret scan; store it only if both pass. Updates and overlay re-tests use it plus fresh discovery samples when available. Keep the sandbox `pmx_` index retention at most 30 days and follow Q24 for removing a job's events.
- Migration from v1: move every kept package from the runs folders into the store, verifying each against `ta_versions.sha256`; report a missing or mismatching one, never skip it silently.

## Overlays (design 7.18)
- Overlay add-ons `TA-parsemaxxing-overlay-<vendor>-<product>` hold only the delta for another app's sourcetype stanzas. Use only the precedence rule the lab proved (Q23). The gate reads the effective settings back from the sandbox (with the owning add-on installed at the production version) and fails any overlay setting that does not take effect. Never modify the owning add-on; v2 overlays cover props, transforms, eventtypes and tags only.

## Topology and connectivity
- Supported Splunk Enterprise versions are 10.2 and later (D10), kept in `environments/versions.py` with the CIM compatibility table (Splunk 10.2 to 10.6: CIM 6.3.0 or later; 10.7 and later: 8.5.0 or later). Below the minimum, block the CIM stage and CIM plan checks for that environment with a message naming the minimum; parsing-only runs continue. The CIM normalizer must read 6.x and 8.x definitions the same way, with tests for each. The connectivity test refuses an older node with a clear message; lab probes run on 10.2 and 10.6 and record any per-version difference.
- Auto-discovery reads `server/info`, `server/roles` and the cluster and SHC status endpoints from one entry node and proposes nodes; it never adds one without admin confirmation.
- Connectivity checks: DNS, TCP, TLS with certificate validation (on by default), token auth, capabilities vs what that node's purpose needs, version, cluster role, token expiry; relay host key and `status`.
- Generate the Splunk role and user creation script for each environment's `parsemaxxing_read` and `parsemaxxing_deploy` accounts from the narrowest capabilities the lab proved. Parsemaxxing never creates roles in production itself.

## Delivery and verification
- One adapter per target: standalone (REST), SHC deployer, deployment server that serves HFs, HF directly (including an HF that is also the UF deployment server); no cluster manager or indexer adapter (D11); each with `plan`, `handoff_bundle`, `deliver` (managed), `verify`, `rollback`. Use only paths the lab proved (Q12–Q17); undocumented endpoints only behind a version check and a lab-recorded result.
- Connections (design 7.1): REST API on 8089 with per-purpose tokens for everything read-only and for direct installs where the lab proves it; SSH only to the relay on the SHC deployer and, if REST cannot do it (Q14), on the DS for HFs; handoff mode uses the read token only; the only inbound connection is the drift webhook. Preview on production is always the second option after the sandbox test and never approves anything on its own. Shared MSSP environments (design 7.1, 7.2): clients are isolated only by their indexes (naming convention `cus_<client>_*` or similar) and their own HFs (each with at least one HF-DS); search heads are shared and can search everything. Deploying for one client sends the index-time part only to that client's HFs and the search-time part to the shared search heads, after the shared search head check passes for every client sending that sourcetype (search-time preview: settings turned into inline SPL, run read-only per client through the tenant base search). Layouts (design 7.1): one or a few HFs where one is the HF-DS (deployment server for UFs on an HF host), or many HFs with a dedicated deployment server for them plus the HF-DS. An HF that is a client of a DS for HFs gets the package through it; every other HF, the HF-DS usually included, gets it directly. Tier rule (design 7.2, D11): the same package goes to every search head (deployer for a cluster, direct for each non-clustered SH) and to the heavy forwarders that receive the data (through the deployment server that serves HFs, otherwise direct; an HF that is also the UF deployment server gets it in its own apps). Never to indexers, never into a UF-serving deployment server's `deployment-apps`, never to a server class with UF clients (check the clients before mapping). Data reaching indexers without an HF: deliver the search-time part, mark index-time "not deliverable". Roll out HFs first, then search heads, verifying each tier before the next. Routing transforms only on HFs. The plan states why each target is in or out.
- Impact analysis is read-only: name collisions, `local/` overrides (read from a member for SHC), restart need, and in MSP shared environments every customer index receiving the sourcetype.
- Verification never retries a push; it reports and offers rollback.
- Rollback goes to **any** registered version: the adapter installs that version's stored bytes from `ta_store/`; it never deletes or alters newer versions. A revert of index-time settings is reported as affecting only newly indexed data; a revert that removes a routing transform re-runs the negative routing test.

## Relay (`relay/`)
- Stdlib-only Python, runs as the `splunk` user behind an SSH forced command with `restrict`.
- Fixed verbs only; every argument validated by pattern; package hash checked before extraction; safe tar rules (no absolute paths, no `..`, no links, no devices, size caps); writes only inside the target apps directory; append-only local log; anything else refused with a non-zero exit.
- SSH setup (design 7.2): keys only, no password authentication; Ed25519 key per environment and host generated by Parsemaxxing (private key only in the vault) or uploaded by the admin; `authorized_keys` line generated with `from=`, the forced `…/pmx-relay` command and `restrict`, by default for the `splunk` OS user (setup test checks it has a working login shell and write access), or for a dedicated `pmxrelay` user with a forced `sudo -n -u splunk …` and one sudoers line; two separate credentials per relay host: the SSH key (machine login) and a Splunk account or token (splunkd login) for CLI and local REST steps, sent on stdin for one call, never on a command line, in the environment, in files, logs or the console; prefer local REST with the token, else `splunk login` fed on stdin then `splunk logout`, never `-auth` (Q13); host key fingerprint confirmed by the admin and pinned (mismatch refuses every call); the Splunk deploy token passed on stdin for CLI steps only; key rotation with a test before the old key is dropped; request ids shared between the ledger and the relay log.
- Relay output is streamed back line by line with the request id for the live console; mask secrets before it leaves the engine. Never add an interactive shell or a free-form "run command" verb.
- Command library (design 7.2): one versioned template file per task and topology, filled with the environment's real values, no secrets in output; every template lab-checked on 10.2 and 10.6; the handoff runbook is built from the same templates.
- Its own test suite (`make relay-test`) including hostile archives and argument injection.

## Discovery, drift, routing, masking
- Discovery and drift searches use the read account through the tenant base-search helper (code-owned base search, customer index allowlist). An index outside the allowlist is refused before any search.
- Discovery is code only: tstats volume, samples with length and linecount checks, `_time` vs `_indextime`, parser warnings, `fieldsummary`, eventtype/tag/data model presence, props ownership over REST, name quality, shape clustering.
- Drift alert searches come from fixed templates with only the sourcetype and baseline numbers filled in; the monitoring app is deployed through the deployment pipeline.
- Routing gate exception: `TRANSFORMS-` on a generic stanza only with `DEST_KEY = MetaData:Sourcetype`; `[host::]` and `[source::]` stanzas exact; positive and negative tests.
- Masking: consistent, format-preserving, keyed per job, map stored only in the vault; secret patterns redacted and flagged. Property tests prove regex shapes survive masking.
